# cPanel / "Setup Python App" deployment

**Status: prepared, not deployed.** The VPS has not been set up. Nothing here
has been executed against a live host.

This is the path for a **shared cPanel host** such as the one serving
`38.242.207.141` (Sakura Host). It does not use systemd, Gunicorn or nginx, so
none of `deploy/systemd/cdms.service`, `deploy/gunicorn_config.py`,
`deploy/bootstrap.sh` or `deploy/deploy.sh` apply. They are kept intact for the
VPS route.

---

## What runs where

| Concern | VPS route | cPanel route |
|---|---|---|
| App server | Gunicorn via systemd | Passenger (host-managed) |
| Web server | nginx (you configure) | Apache (host-managed) |
| Config file | `/etc/cdms/cdms.env` | `.env` beside `manage.py` |
| Static files | nginx `alias` | Apache, plus WhiteNoise fallback |
| Media | nginx `alias` or S3 | **S3** (see below) |
| Migrations | `deploy/deploy.sh` | Terminal or cPanel run-script |
| Restarts | `systemctl restart cdms` | touch `tmp/restart.txt` |

## Before you start: three things to confirm

These decide whether this route works at all. Check them in cPanel first; do
not start uploading until all three are confirmed.

1. **Does "Setup Python App" exist?** cPanel → **Software → Setup Python App**.
   If it is missing, this route is not available and the only option is a real
   VPS.
2. **Which Python versions are offered?** 3.12 is preferred, matching
   `runtime.txt`. 3.11 will very likely work; 3.10 may need older wheels.
3. **Do you have SSH or a Terminal app?** You need to run `pip`, `migrate` and
   `collectstatic`. On many shared hosts SSH is on a non-standard port and
   reachable only via the cPanel **Terminal** app. Without any shell access
   this route becomes impractical.

## 1. Create the database

cPanel → **MySQL Databases**. Create:

| Field | Value |
|---|---|
| Database | `argentina` (often becomes `cpaneluser_argentina`) |
| User | `argentina_user` (often `cpaneluser_argentina_user`) |
| Password | generated by cPanel |

Add the user to the database with **ALL PRIVILEGES**. cPanel has no
per-table grant UI, and Django migrations need `CREATE` and `ALTER`. Use a
dedicated user: never the account's main MySQL user, never root.

If cPanel prefixed the names, use the prefixed names in `.env` — the exact
value is what matters, not the suggestion above.

## 2. Clone the repository

In the Terminal app, from your home directory:

```bash
cd ~
git clone https://github.com/simonntalila-bot/hopstal-management-systems-.git argentina
cd argentina
```

Use `hopstal-management-systems-`. Never the old repository.

## 3. Create the application

cPanel → **Setup Python App → Create Application**:

| Field | Value |
|---|---|
| Python version | 3.12 (or the highest offered) |
| Application root | `/home/<cpaneluser>/argentina` |
| Application URL | `makongatiarg.co.tz` |
| Application startup file | `hms_project/wsgi.py` |
| Final WSGI method | `application` |

`hms_project/wsgi.py` is the reliable choice because it is inside the
application root. If the host insists on the conventional name, use
`deploy/cpanel/passenger_wsgi.py` as the startup file instead; it is the same
callable with the import paths set up explicitly.

## 4. Add the environment file

The application reads a `.env` file next to `manage.py` before falling back to
real environment variables. On a shared host this is the only dependable way to
supply secrets, because there is no systemd `EnvironmentFile`.

Copy the template and fill it in:

```bash
cd ~/argentina
cp .env.example .env
chmod 600 .env
nano .env
```

Minimum required values:

```
DJANGO_SECRET_KEY=<generate>
DJANGO_DEBUG=0
DJANGO_ALLOWED_HOSTS=makongatiarg.co.tz,www.makongatiarg.co.tz
DJANGO_CSRF_TRUSTED_ORIGINS=https://makongatiarg.co.tz,https://www.makongatiarg.co.tz
DB_NAME=<the prefixed name cPanel gave you>
DB_USER=<the prefixed user cPanel gave you>
DB_PASSWORD=<the password cPanel generated>
DB_HOST=127.0.0.1
DB_PORT=3306
```

Generate the key:

```bash
python3 -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

`DJANGO_SECRET_KEY` is not optional. The application now **refuses to start**
without it rather than fall back to a placeholder that is public in this
repository.

`.env` is gitignored and blocked by the pre-commit guard. Confirm with
`git status` that it does not appear.

## 5. Install dependencies and prepare

In the Terminal, from `~/argentina`:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py check
python manage.py makemigrations --check
python manage.py migrate
python manage.py collectstatic --noinput
```

`collectstatic` is what makes static files appear. WhiteNoise serves them as a
fallback if Apache is not configured, so the site works even before the
`.htaccess` is in place.

## 6. Point the document root at the app

Copy `deploy/cpanel/public_html.htaccess` into the document root cPanel
created, usually `~/public_html/.htaccess`:

```bash
cp deploy/cpanel/public_html.htaccess ~/public_html/.htaccess
```

It routes non-file requests to Passenger, serves static files from disk, and
disables script execution inside `/media/`.

## 7. Media: use S3, do not use local disk

On this route there is no nginx `alias`, and Django would serve every
ultrasound image and scanned document through the Python process. That is slow
and memory-hungry for exactly the files a hospital accumulates.

Set these in `.env` and uploads go straight to object storage:

```
AWS_STORAGE_BUCKET_NAME=<bucket>
AWS_ACCESS_KEY_ID=<key>
AWS_SECRET_ACCESS_KEY=<secret>
AWS_S3_REGION_NAME=<region>
AWS_QUERYSTRING_AUTH=1
```

`AWS_S3_ENDPOINT_URL` is only needed for a non-AWS provider such as Backblaze
B2, Wasabi or a Tanzanian host. Leave it unset for AWS. Use a dedicated IAM
user scoped to that one bucket, never root credentials.

## 8. Backups on a shared host

cPanel → **Cron Jobs**, daily. The scripts run without root:

```bash
15 2 * * * cd /home/<cpaneluser>/argentina && BACKUP_DRY_RUN=0 bash scripts/backup_mysql.sh >> /home/<cpaneluser>/cdms-backup.log 2>&1
```

Put `MYSQL_CNF` and `BACKUP_ENCRYPT_PASSPHRASE_FILE` in your home directory at
mode 600, outside the repository. Keep the 30/12/12 retention from
`docs/DATABASE_BACKUP.md`, and rely on the bucket lifecycle rule for the weekly
and monthly tiers, exactly as on the VPS.

## 9. After any change: restart Passenger

```bash
mkdir -p ~/argentina/tmp
touch ~/argentina/tmp/restart.txt
```

## Known limits of this route

- **Shared CPU and memory.** A hospital system with several users logging in
  at once can be slowed by other tenants on the same server.
- **No control over the web server.** Header, timeout and upload-size changes
  depend on what the host allows.
- **One application per account** in many plans.
- **Backups are the account holder's job.** A cPanel account can be suspended
  for non-payment, which takes the database with it. Offsite copies are not
  optional here.
- **Email credentials** come from the host's mail server, not Gmail.

None of these make it unusable, but they are the reasons the VPS route is
better for a production hospital system. This route is a way to get the system
in front of users now, on the host already paid for.
